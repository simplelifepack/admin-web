Decisions locked for this build (11 Oct 2026):
- Built alongside the existing `/coffee/packages` stopgap, not replacing it yet.
- Admin Google Sign-In reuses the existing shared dev OAuth client (`frontend-web/.env.example`'s `VITE_GOOGLE_CLIENT_ID`).
- Admin API lives in `backend/` under `/admin/v1/*` (D1). Admin frontend is this new `admin-web/` repo, same pattern as `frontend-web/` (Vite + React + TS + Redux Toolkit).
- Generic `Job` table modeled on the existing `CustomPackageGenerationJob` lease/retry pattern.
- Passkey (WebAuthn) is real, not stubbed — localhost is a valid relying party for browser testing.
- A "Test as Admin" dev bypass exists alongside (not instead of) real Google Sign-In, 12 Oct — skips Google + passkey, 403s outside local dev, logged distinctly as `auth.dev_login`. Implementation convenience, not a design decision — not reflected in the design doc.

- [x] Scheduled audit-chain verification (13 Oct). Built as a new `audit_chain_verify` `JobType` on the existing `Job` table — reuses the Phase 2 job-runner model purely for persisted history and, more importantly, the already-built `evaluateJobFailedAlerts` hook, rather than inventing a second alerting path for one more "something went wrong" case.
  - **Structurally different from the other three job types, by design**: `key_rewrap`/`storage_audit`/`package_source_backfill` chunk over customer data (potentially huge), so they're born `running` and advance tick by tick. `verifyAuditChain()` already walks the whole `AdminAuditLog` table in one pass, and that table's size is bounded by admin team activity, not customer data — so a run always completes synchronously; the `Job` row this creates is born already `completed` or `failed`, never `running`, and has no tick/pause/resume state to ever reach. Added an explicit `assertTickable` guard there so a stray `/jobs/:id/tick` call against an `audit_chain_verify` id fails with a clear 400 instead of silently falling through to the wrong job service (a real bug the TypeScript compiler caught immediately — the generic dispatcher's capability maps didn't have an entry for the new type, which is exactly the kind of mismatch that guard now prevents going forward too).
